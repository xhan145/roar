# ROAR pricing $19/$29/$49 + Stripe-ready static site — Design

**Date:** 2026-07-28 · **Status:** approved · **Repo:** `xhan145/roar`

## Goal

Move paid pricing to **Core free / Pro $19 / Developer $29 / Supporter $49**
(one-time), centralise it, rebuild the public pricing page, and make checkout
Stripe-ready **without a server** — because the site is static HTML on GitHub
Pages.

## Architecture discovered

- **Desktop app:** flat-module Python (tray + pywebview settings), frozen with
  PyInstaller.
- **Commercial layer:** `commercial_config.py` (prices, purchase URLs, public
  key), `entitlements.py` (feature→edition map, `core/pro/developer/supporter`),
  `license.py` (offline Ed25519 verify), `access.py` (runtime gates, LIVE),
  `upgrade_prompts.py` (copy consuming the price constants).
- **Website:** `site/index.html` — a single static page deployed by
  `.github/workflows/pages.yml` (`path: site`) to GitHub Pages.
  **No backend, no serverless functions, no build step.**
- **Signing key:** `~/.roar-signing/roar_license_private_key.pem`, deliberately
  outside the repo; `scripts/issue_license.py` signs manually.

## Decisions (user-approved)

1. **Checkout = Stripe Payment Links.** No server required. Payment Links are
   *public* URLs (unlike Price IDs); the amount is fixed inside Stripe, so the
   browser cannot tamper with price — the same protection the brief wanted from
   server-side price mapping.
2. **Fulfilment = manual delivery + a typed stub.** `scripts/issue_license.py`
   stays the real path; a `fulfillment.py` boundary documents and *explicitly
   fails* the automated path so nothing pretends to be secure.
3. **Not built (documented instead):** `POST /api/checkout`, Stripe webhook,
   server-side session creation. GitHub Pages cannot execute them.

## Components

### 1. Pricing source of truth — `commercial_config.py`

```python
PRICING = {
  "core":      {"display_name": "ROAR Core",      "price_usd": 0,  "price_label": "Free",     "purchase_url": None},
  "pro":       {"display_name": "ROAR Pro",       "price_usd": 19, "price_label": "$19 once", "purchase_url": ...},
  "developer": {"display_name": "ROAR Developer", "price_usd": 29, "price_label": "$29 once", "purchase_url": ...},
  "supporter": {"display_name": "ROAR Supporter", "price_usd": 49, "price_label": "$49 once", "purchase_url": ...},
}
```

- Edition IDs stay stable and machine-readable; **prices are never entitlement
  identifiers**.
- `PRO_PRICE_USD` / `DEVELOPER_PRICE_USD` / `SUPPORTER_PRICE_USD` remain as
  values *derived* from `PRICING`, so `upgrade_prompts.py` and existing tests
  keep working (no scattered duplication).
- `PURCHASE_URL_*` point at the public pricing page with an edition anchor
  (`…/#pricing`), never at a Stripe URL — the site owns checkout.

### 2. Entitlements — unchanged code, new tests

`core < pro < developer <= supporter` already exists and gates are live, so no
structural change. Add tests asserting: Supporter inherits Developer, Developer
inherits Pro, Pro inherits Core, unknown editions resolve safely, and Core keeps
privacy controls, history deletion and audio deletion.

### 3. Pricing page — `site/index.html`

Four cards (Core / Pro / Developer / Supporter) with the approved copy, subtle
"Best for most people" (Pro) and "Best for developers" (Developer) labels, and a
trust strip: **One payment. No subscription.** plus no account, no cloud
transcription, no telemetry, offline licence verification, purchased version
keeps working, all v1.x updates, optional paid major upgrades later.

Accessibility: semantic heading order, real `<a>`/`<button>` elements, visible
focus rings, contrast-safe, no colour-only meaning, cards stack on narrow
screens, price text does not wrap awkwardly, reduced-motion respected.

### 4. Checkout — Payment Links with graceful pre-Stripe behaviour

The site's existing config block already models this:

```js
purchase: { pro: "", developer: "", supporter: "" }   // "" => pre-order email
```

Filling each with its Stripe Payment Link is the whole integration. While empty,
buttons fall back to the existing pre-order email — never a silent `#`. No
secret key, no webhook secret, no Price IDs in the repo.

### 5. Purchase outcome pages

`site/purchase/success.html` — reachable via the Payment Link redirect. Copy:
"Purchase received. Your ROAR license will be delivered using the fulfilment
process connected to this checkout." It must **never** claim a licence was
already emailed. Links to download and activation help.
Cancellation is a state on the pricing page (`?checkout=cancelled`): "Nothing was
charged."

### 6. Fulfilment boundary — `fulfillment.py`

```python
issue_license(edition, stripe_session_id, customer_email, major_version)
    -> LicenseDeliveryResult
```

Raises an explicit, safe failure (no signing here). Documents that production
must: confirm payment with Stripe, validate the edition, enforce idempotency on
the session ID, sign with the existing offline format **on a secure server**,
deliver securely, store no voice/transcript/usage data, and follow a documented
refund policy.

### 7. Documentation

`docs/PRICING.md`, `FEATURE_MATRIX.md`, `MONETIZATION.md`, `README.md`,
`CHANGELOG.md` updated to the new tree; new `docs/STRIPE_SETUP.md` (Payment
Links variant, with the warning that payment completion ≠ licence delivered);
new `docs/WEBSITE_IMPLEMENTATION.md` recording the server-side contract for a
future host.

## Testing

- **Pricing:** core 0, pro 19, developer 29, supporter 49; `PRICING` is the only
  definition; derived constants agree.
- **Stale-copy:** relationship-based, not blind number bans — assert no
  "Supporter … $99", no "Pro … $29", no "Developer … $49" in customer-facing
  files, while `$29`/`$49` remain valid for their new editions.
- **Consistency:** `site/index.html` and `docs/PRICING.md` display exactly the
  canonical labels.
- **Entitlements:** inheritance chain + Core-free invariants.
- **Checkout config:** paid editions expose a purchase URL or degrade to the
  pre-order fallback; `core` is never purchasable; no `sk_`/`whsec_` secret
  pattern anywhere in the repo.
- **Fulfilment stub:** fails explicitly; never signs.

## Invariants preserved

Core stays genuinely useful and free; dictation never needs a licence; no
account, no cloud transcription, no telemetry, no subscription; privacy and
deletion controls are never paid-only; licensing code never reads transcript,
audio, history, clipboard, vocabulary or insight data; validation stays offline.

## Out of scope

Server-side checkout/webhook (impossible on GitHub Pages), subscriptions,
accounts, automated licence signing, hosting migration, runtime-gate changes.
